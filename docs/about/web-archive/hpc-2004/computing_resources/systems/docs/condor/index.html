What is Condor?

Condor is a job submission facility that manages and schedules a pool of computing resources in a manner that focuses on High Throughput Computing (HTC). High Throughput Computing supports a large amount of processing capacity sustained over a very long period of time. Condor, in focusing HTC, allows users to submit jobs which are then executed using idle cycles on machines otherwise not being used. Whenever the load on the machine exceeds a certain predefined level or the mouse or keyboard is activated, Condor will remove any processes on that machine and not schedule it further. Condor programs are linked with checkpoint code that allows them to be unloaded from one machine and restarted, from where they left off, on another. Probably the best way to describe how Condor implements HTC is to use the terms "bottom feeder" or "cycle stealing" system. Condor supports both parallel (MPI/PVM) as well as serial jobs.

The idea behind condor is to allow users to submit jobs which are then executed using idle cycles on machines otherwise not being used. These machines are usually assumed to be "owned" by individuals who have the machines on a local area network. The "owners" wish to share and pool these machines together to provide in effect a large computing resource which is made available when the owners are not using the machines. Thus, whenever the load on the machine exceeds a certain predefined level or the mouse or keyboard is activated, Condor system will remove any processes on that machine and not schedule it further.

Projects

"Flocking Pools" Currently, we have been connecting the HPC@UNM pool with one of the pools at the University of Wisconsin. Jobs submitted to either pool can run on available resources in the other pool. The pools are set up so that if a job submitted to one pool has no available resources and the other pool does, the jobs will migrate to the second pool. Preemptive criterion have been established so that jobs submitted to a particular pool from accounts in that pool have preference to run in that pool over jobs from "outside" pools. For example, if a job is submitted to the University of Wisconsin's pool and that pool is busy with jobs with accounts from the HPC@UNM pool, the HPC@UNM jobs are check-pointed and migrated out of the University of Wisconsin's pool,  allowing the newly entered job from the CS department's pool to run. The check-pointed jobs may then run later on any available machine of the same architecture when one becomes available.

Experience with Condor

Condor has been very reliable and robust and has provided an effective computational service to HPC@UNM users that complements and supplements our relatively large parallel systems. Computations that do not require specialized high performance networking capabilities but run for a long time or represent a large number of jobs are best done on the Condor pool.
