Parallel Environments

  • IBM SP1, SP2 and workstation clusters are examples of distributed memory MIMD machines
  • MIMD - Multiple Instruction, Multiple Data - each processor runs independently on its portion of the data
  • distributed memory - each processor has its own memory that only it can directly access
  • Goal: coordinate the operations of the various processors on a problem in a way that improves the performance of a code and that scales to increases in numbers of processors, amount of memory and I/O capacity

Message Passing

Coordination of tasks in a distributed memory MIMD environment involves

  1. synchronizing tasks - do the right thing at the right time
  2. sharing data - a task may need data assigned to or produced by another task, or may need to give data to other tasks

Message passing is the mechanism to achieve these requirements

( Click here for more information on message passing in PVM. )

Message Passing Systems

Message passing library Software package to initiate and coordinate tasks on a distributed memory machine.

  • machine dependent - MPL (EUI), ...
  • portable - PVM, P4, MPI, chameleon

PVM Terms

Host : a physical machine (or nodes of a parallel machine)

Virtual Machine : meta-machine composed of one or more hosts

Task : a PVM process - smallest unit of computation

TID : unique identifier associated with each task

PVMD : the PVM daemon, 'pvm3/lib/ARCH/pvmd3'

Message : ordered list of data sent between tasks

Group : set of tasks assigned a symbolic name, each task has a unique index in the group and a task can belong to zero or more groups

PVM Overview

PVM (Parallel Virtual Machine)

A software package that permits a heterogeneous collection of computers on a network to appear as one parallel machine.
  • a collection of workstations with ethernet connections
  • a collection of computers with internet connections
  • the nodes of an IBM SP1 or SP2
  • hybrids of differing machines with various connections

Heterogeneity

PVM exploits heterogeneity at three levels: Application, Machine and Network

Application

subtasks can be written for the architecture best suited to their solution (serial, vector, massively parallel)

Machine

machines with different architectures, operating systems and data formats can be collected together to form a single virtual machine

Network

the machines can be connected by different networks (FDDI, token ring, ethernet, high performance switch)

Major Features

  • any user can install PVM under his home directory
  • easy to configure virtual machine using host files
  • easy to write programs - fairly small number of routines
  • C and Fortran routines
  • multiple applications can run simultaneously on one VM
  • PVM package is small - a few Mb of disk space

Portability

  • PVM source code is very portable across Unix machines
  • PVM currently runs on
    • 80386/486 with BSDI
    • DEC Alpha/OSF-1
    • DEC Micorvax
    • DECstation
    • DG Aviion
    • HP 9000/300
    • IBM RS/6000
    • Silicon Graphics IRIS
    • Sun4, Sparc
    • and on 17 more different computer architectures
  • version 3 portable to non-Unix machines

PVM System

The PVM System is composed of:

a daemon program pvmd3

  • libpvm programming library
  • user applications

A console ( either GUI based or character mode) is available for controlling the virtual machine. It may be started up by typing pvm or xpvm at the unix prompt ( assuming the paths have been set correctly ). The console maybe used to add hosts, spawn tasks, delete hosts etc. ( more details to follow)
( Click here for more information. )

A virtual machine is configured by starting the daemon program on all of the intended hosts, one daemon runs on each host for each user.

The daemon program:

  • provides inter-host point of contact
  • authenticates tasks
  • executes processes on host
  • provides fault detection
  • is mainly a message router

The libpvm programming library:

  • linked with each application
  • small number of routines (simplicity)

Applications:

  • written by user in PVM message-passing calls
  • executed as PVM ``tasks''

PVM Library

  • routines in both Fortran and C
  • C programs: include pvm3.h and link to library libpvm3.a
  • Fortran programs: include fpvm3.h and link to libraries libpvm3.a and libfpvm3.a
  • if group routines are used, link to libgpvm3.a
  • see makefile accompanying examples

Fortran Library

all programs should have

  • pvmfmytid() - first PVM statement, enrolls program in PVM, gets tid of the program Equivalent C function: pvm_mytid()
    This function returns the task identifier number (tid) of the calling PVM process. This value, if less than 0, indicates an error.
    tid: is a 32 bit integer created by local pvmd, encoding much information about the process.
  • pvmfexit() - last PVM statement, disenrolls program from PVM, program may continue with further computations. All programs should call this.
    Equivalent C function: pvm_exit() This function must be called by processes not started by pvm_spawn() ( pvmfspawn() in Fortran ) - otherwise, PVM has no way of knowing if the process has stopped normally or crashed. A status code is returned by this function, and values less than zero indicate an error.

Additionally, PVM programs perform process control by starting and stopping tasks

  • pvmfspawn()- start tasks and assign each task a unique tid
    Equivalent function in C: pvm_spawn()
    A number of arguments are taken in, including the executable filename for the PVM process to be started, and an integer indicating the number of PVM tasks started is returned. A negative return value indicates an error.
  • pvmfparent() - get tid of parent task
    Equivalent function in C: pvm_parent()
    The tid of the process that spawned the calling process is returned. If the calling process was not created with pvm_spawn, the the returned value is set to PvmNoParent.
  • pvmfkill() - stop a PVM task
    Equivalent function in C: pvm_kill( int tid )
    The function takes as input the tid of the PVM process to be killed and returns a status code. A negative status code indicates an error.

Fortran Library - Message Passing

Sending is a three step process:

  1. pvmfinitsend() - initialize send buffer
    Equivalent C function: pvm_initsend(int encoding)
    encoding     specifies the message encoding scheme to be used. An integer id to the buffer for packing the data into is returned.
  2. pvmfpack() - pack data into buffer (any number of times)
    Equivalent C function: pvm_pk*()C has many functions according to the data type to be packed in. The functions, in Fortran or C, take a number of arguments, and return a status code. A negative return value would indicate an error.
  3. pvmfsend() - send message to desired process
    Equivalent C function: pvm_send() The function takes in a tid to the destination process and a positive integer message tag supplied by the user,allowing the program to distinguish between different messages. The function returns an integer status code, and a negative value indicates an error.

Note: pvmfsend can be replaced by any other send routine such as pvmfmcast, see User Guide

Receiving: for every send there should be a receive, and for every pack there should be a matching unpack

  1. pvmfrecv() - receive a message (blocking receive) Equivalent C function: pvm_recv()The function takes in as input a tid of the sending process, and a positive integer message tag supplied by the user. The function returns an id for the new active receive buffer. A negative value signals an error.
  2. pvmfunpack() - unpack data from buffer Equivalent C function: pvm_upk*()C has a number of functions to match the type of data to be unpacked. The function takes in a number of arguments, and returns a status code, which, if negative, signals an error.

Note:there are nonblocking as well as blocking receives, see User Guide

Once composed, a message can be:

  1. sent to another task, multicast to a list of tasks or broadcast to a group
  2. sent any number of times without repacking
  • PVM sends are non-blocking, returns ASAP, does not imply receipt
  • messages are downloaded to receiving task and queued
  • receive operation searches queue for match and removes it from the queue
  • messages sent between two tasks arrive in order sent

Fortran Library - Group Routines

  • optional library to provide naming structure
  • tasks can enroll in a group and can be addressed by the group name and an index
  • group routines:
    • join, leave groups
    • lookup group member
    • broadcast to group
    • perform barrier synchronization within group

A Basic Parallel Problem

Problem: Compute the entries of a matrix where

  • the computation is CPU intensive
  • the entries can be computed independently of one another

Goal: parallelize this problem, along the way, consider the issues of load balancing and task granularity

A Basic Parallel Problem

The serial code sermat.f contains the lines

do 10 i = 1,n
do 10 j = 1,n
mat(i,j) = setmat(i,j)
10   continue

To parallelize, we will divide up this calculation into tasks, and assign the computation to the various processors

Parallel Strategies

  • strategy 1, static load balance: given N processors, divide matrix into N equal parts, have each processor compute one of the parts

in this strategy, the speedup is limited by the slowest processor we want the faster processors to get more jobs

  • strategy 2, dynamic load balance: each processor computes an entry of the matrix at a time, when it completes this task, it determines the next entry to be computed and repeats until all entries are completed

still have a problem here, the task granularity is too small, the speedup is limited by the communications

PVM hostfile

Your PVM hostfile defines your parallel virtual machine. It contains the names of all desired machines, one per line, and only needs to reside on the machine where you start PVM

  • The filename can be whatever you like (eg. hostfile3)
  • Comment lines start with "#"
  • Options include:
    • & = must precede hostname if the host is to be added dynamically later
    • ep = executable program component paths if not using default
    • dx = daemon path if not using default ~/pvm3/bin/PVM_ARCH
    • lo = login userid
    • pw = password entry required
    • * = apply to all following hosts in hostfile

 

########################################################
# FILENAME:  hostfile.2
# DESCRIPTION: PVM hostfile with a few options
########################################################

fr29s01.mhpcc.edu
fr29s02.mhpcc.edu
fr29s03.mhpcc.edu
fr29s04.mhpcc.edu

#
# 	next two hosts will be may be added dynamically later
#

&fr10n12.mhpcc.edu
&fr12n14.mhpcc.edu

#
# next host has different path for its PVM executables
#

beech.tc.cornell.edu  ep=/u/user02/pvm/testing/bin

#
# next line applies to all hosts which follow it
#

* lo=user02 pw

kanaha.mhpcc.edu
makena.mhpcc.edu
littleb.mhpcc.edu

Troubleshooting PVM3.3.x

The following is a troubleshooting list for the setup of PVM:

  1. pvmgs file from earlier version still in $HOME/pvm3/bin/RS6K. Delete it. (Causes mksocs connect error?)
  2. .rhost file write able by others. rw-r--r-- is correct. To identify this problem, try rlogin to another AHPCC machine. If it prompts you for a password, .rhosts is setup incorrectly.
  3. Path not set before "not interactive shell" exit in the .cshrc file. Test with rsh pvmd3. If it cannot find pvmd3, the path is not set before the "not interactive shell" exit.
  4. Path not set up or environment not set up properly in .cshrc file. Use printenv to check path and environment. They should all show pvm3 (or the version of pvm being used).
  5. pvmd.xxx files. Pvmd's cannot startup if a pvmd.xxx file exists in the /tmp directory. Since /tmp filesystems exist on each machine, you should check on each machine.
  6. Xpvm does not come up with list of hosts. .xpvm_hosts file does not exist or is set up improperly.
  7. Old programs don't run. Programs must be recompiled under the new pvm to run. Note that the include files have also changed.
  8. Korn shell. Korn shell does not read the .cshrc file on startup. In order to run under the korn shell the following statement is necessary in your .profile:
    export PVM_DPATH=$PVM_ROOT/lib/pvmd
  9. Interactive statements in the .cshrc. The interactive statements block the running of the .cshrc on the remote system when it is started up. If interactive commands are needed, put them in the .login or after the "if not interactive shell" exit in the .cshrc.
  10. Be careful of concurrent I/O to the same files in a shared filesystem! For concurrent I/O (writing) in a shared filesystem, you may want to implement a scheme to assign unique names to output files.
  11. For the most recent PVM versions, stdout and stderr from spawned processes are written to your /tmp/pvml.uid file. Only stdout and stderr from parent process will appear on your screen. This will be "fixed" in future releases of PVM. A workaround is to use the PVM interactive console and the "->" option with the spawn command, or to use XPVM.
  12. On independent file systems, you must maintain all of the different versions of your executables on multiple machines.
  13. Make sure all pvmd3s and PVM libraries are the same PVM version.
  14. Always use full domain names in .rhosts and PVM hostfiles.

SPMD driver

part 1 include file fpvm3.h

	include 'fpvm3.h'

part 2 declare PVM variables

	integer mytid,ptid,me,info,inst,igrpsize
	integer numt,nhosts,njobs,narch,dtid,speed
	character host,arch
	parameter (mnproc = 4)
	integer tids(0:mnproc)

part 3 enroll in PVM

	call pvmfparent(ptid)
	call pvmfmytid(mytid)

part 4 determine number of jobs running

	call pvmfconfig(nhosts,narch,dtid,host,arch,speed,info)
	njobs = nhosts + 1

part 5 find out if parent or child

	call pvmfjoingroup('strat3grp',inst)
	call pvmfgsize('strat3grp',igrpsize)

part 6 parent process

	tids(0) = mytid
	me = 0
c start copies ...
	call pvmfspawn('strat3',PVMDEFAULT,'*',njobs-1,tids(1),numt)

part 7 child process

	me = inst
	tids(me) = mytid
	tids(0) = ptid

part 8 synchronize processes

	call pvmfbarrier('strat3grp',njobs,info)
	call pvmflvgroup('strat3grp',info)

part 9 exit pvm

	call pvmfexit()

work subroutine

part 1 subroutine header and include

	subroutine parmat(me,tids,mnproc,njobs)
	include 'fpvm3.h'

part 2 declare PVM variables

	integer me,mnproc,njobs,mytid,ctid,irow
	integer tids(0:mnproc)

part 3 child computes rows

	if (me .gt. 0) then
  	   mytid = tids(me)
 	   irow = me
5      	continue

part 4 send results to parent

	call pvmfinitsend(0,info)
	call pvmfpack(INTEGER4,mytid,1,1,info)
	call pvmfpack(INTEGER4,irow,1,1,info)
	call pvmfpack(REAL4,mat(irow,1),n,nmax,info)
	call pvmfsend(tids(0),2,info)

part 5 receive next job from parent

	call pvmfrecv(tids(0),3,info)
	call pvmfunpack(INTEGER4,irow,1,1,info)
	if (irow .le. n) goto 5

part 6 receive results from child

	else
	do 6 icnt = 1,n
 	  call pvmfrecv(-1,2,info)
	  call pvmfunpack(INTEGER4,ctid,1,1,info)
	  call pvmfunpack(INTEGER4,irow,1,1,info)
	  call pvmfunpack(REAL4,mat(irow,1),n,nmax,info)

part 7 send next job to child

	  irow = icnt + njobs - 1
 	  call pvmfinitsend(0,info)
 	  call pvmfpack(INTEGER4,irow,1,1,info)
 	  call pvmfsend(ctid,3,info)
6 	continue

pi Calculation

This program calculates pi using a "dart board" algorithm. See Fox et al.(1988) Solving Problems on Concurrent Processors, vol.1 page 207. In the parallel version, all processes contribute to the calculation, with the master averaging the values for pi.

Concurrent Wave Equation

This program implements the concurrent wave equation described in Chapter 5 of Fox et al., 1988, Solving Problems on Concurrent Processors, vol 1.

A vibrating string is decomposed into points. Each processor is responsible for updating the amplitude of a number of points over time. At each iteration, each processor exchanges boundary points with their nearest neighbors.

An X based display of the final wave is provided.

PVM Files:

  • FORTRAN: pvm_wave.f, pvm_wave.h, draw_wave.c, make.pvm_wave.f
  • C: pvm_wave.c, draw_wave.c, make.pvm_wave.c

2D Heat Equation

This example is based on a simplified two-dimensional heat equation domain decomposition. The initial temperature is computed to be high in the middle of the domain and zero at the boundaries. The boundaries are held at zero throughout the simulation. During the time-stepping, an array containing two domains is used; these domains alternate between old data and new data.

  • Serial Files:
    • FORTRAN: ser_heat2D.f and make.ser_heat2D.f
    • C: ser_heat2D.c and make.ser_heat2D.c
  • PVM Files:
    • FORTRAN: pvm_heat2D.f, pvm_heat2D.h, draw_heat.c, make.pvm_heat2D.f
    • C: pvm_heat2D.c, draw_heat.c, make.pvm_heat2D.c

Timing Example

This example is a communication timing test for PVM.

A set number of messages are sent between the master and worker tasks. Before and after timings are made for each message and an average is calculated when completed.

PVM Files:

  • FORTRAN: pvm_timing.master.f, pvm_timing.worker.f, make.pvm_timing.f
  • C: pvm_timing.master.c, pvm_timing.worker.c, make.pvm_timing.c

Load Balancing

This example demonstrates simple load balancing for PVM.

A matrix is sent by the master to each worker task. Each worker task computes the inverse of its matrix and returns the result to the master. As the master receives each result it sends a new matrix to that worker.

PVM Files:

  • FORTRAN: hitc.f, hitc_worker.f, make.hitc.f
